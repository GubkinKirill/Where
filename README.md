# Учёт техники и комплектующих

Веб-приложение для учёта компьютерной техники, комплектующих и одноплатных компьютеров
на небольшом предприятии. Разворачивается внутри локальной сети, в интернет не выставляется.

Масштаб: около 20 компьютеров, 150–300 единиц учёта, до 10 одновременных пользователей.
Приоритет — простота сопровождения, а не масштабируемость.

## Главная идея

**Компьютер и комплектующее — одна и та же сущность.** Системный блок, монитор, планка
памяти, SSD, блок питания, Raspberry Pi — всё это `Item` (единица учёта). Отличаются только
типом и набором атрибутов.

Разница между «компьютером» и «комплектующим» выражается не таблицей, а размещением:
планка памяти внутри системного блока — это комплектующее в его составе; та же планка
на полке шкафа — позиция склада. При перемещении запись не дублируется, меняется размещение.

Размещений семь видов: внутри другой единицы, на складе, у сотрудника, в кабинете,
в командировке, передано за пределы отдела, списано.

**Где вещь и чья вещь — разные вопросы.** Размещение выводится из журнала и меняется
только перемещением. Принадлежность — поле `Item.project_id`: пусто значит «числится
на предприятии», иначе единица пришла из проекта и остаётся его, где бы ни лежала.

**Текущее размещение нельзя отредактировать формой.** Оно вычисляется из журнала
перемещений: любое изменение — это новая запись в журнале, единственная точка входа —
сервисная функция `move_item()`. Поле размещения в `Item` — денормализованный кэш,
который обновляет только она.

## Стек

Python 3.11+ · FastAPI · SQLite + SQLAlchemy 2.x · Alembic · Jinja2 + HTMX ·
Pydantic v2 · pytest.

Фронтенд-сборщиков нет: серверный рендеринг плюс HTMX, один статический CSS-файл,
никаких npm-зависимостей. Приложение запускается одной командой без предварительной сборки.

## Кто что видит

Четыре роли. Первые три — технический отдел, они работают с учётными экранами;
четвёртая ведёт только в личный кабинет.

| Роль | Что доступно |
|------|--------------|
| `admin` | всё, включая справочники, шаблоны комплектности и учётные записи |
| `editor` | единицы, перемещения, выдачи и возвраты |
| `viewer` | просмотр списков, карточек, отчётов |
| `employee` | только `/cabinet`: своя техника, коллеги, поиск вещи |

Учётная запись с ролью `employee` обязательно привязана к карточке сотрудника — кабинет
строится вокруг человека, за которым числится техника, и без карточки показывать нечего.
На одного человека — одна учётная запись.

## Прототип интерфейса

Статические макеты в `prototype/` — карточка единицы, список с фильтрами, форма выдачи.
Бэкенда не требуют:

```bash
cd prototype
python3 -m http.server 8077 --bind 127.0.0.1
```

Затем открыть <http://127.0.0.1:8077/item.html>.

## Установка и запуск

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt

cp .env.example .env          # и поправить BASE_URL и SECRET_KEY
alembic upgrade head          # создать структуру БД

uvicorn app.main:app --host 0.0.0.0 --port 8000
```

Приложение на <http://localhost:8000>. Сборка фронтенда не нужна: HTMX и CSS лежат
статическими файлами в `app/static`.

### Демо-набор отдельной базой

Демо-данные держатся в собственном файле, чтобы боевая база оставалась чистой.
`DB_PATH` переключает и миграции, и приложение:

```bash
DB_PATH=data/demo.db alembic upgrade head
DB_PATH=data/demo.db python -m scripts.seed_demo
DB_PATH=data/demo.db uvicorn app.main:app --port 8000
```

В наборе — 32 единицы во всех видах размещения, три проекта, три командировки
(просроченная, только что выехавшая и закрытая), склад и расходники.
Наигрались — `rm data/demo.db*`, боевая база не тронута.

Учётные записи демо-набора: `admin / admin12345` (администратор),
`kgubkin / editor12345` (редактор), `viewer / viewer12345` (просмотр),
`petrov / employee12345` и `novikov / employee12345` (личные кабинеты;
Новиков как раз в командировке).
### Тестовое наполнение поверх своей базы

Когда сотрудники уже заведены, а потренироваться не на чем, техника добавляется
к ним, не создавая ни одной учётной записи:

```bash
python -m scripts.seed_sandbox
```

Скрипт берёт тех сотрудников, что есть в базе, и раздаёт им рабочие места, заполняет
склад, заводит три проекта и три командировки и расходники. Учётки и карточки
сотрудников не трогаются — скрипт сверяет их число до и после и откатывается, если
оно разошлось. Если единицы уже заведены, он откажется работать: дописывать тестовое
к боевому учёту нельзя.

Убрать потом — тем же `reset_db` с `--keep-types`, чтобы типы единиц остались.


Боевые учётные записи заводят в интерфейсе — «Учётки» в шапке, только у администратора.
Пока войти некому, есть та же операция из командной строки:

```bash
python -m scripts.create_admin ivanov --role admin --full-name "Иванов И. И."
python -m scripts.create_admin petrov --role employee --employee 1042   # табельный номер
```

Тесты:

```bash
pytest
```

## Развёртывание на сервере

### Почему не PostgreSQL

База остаётся SQLite, и это осознанный выбор под здешнюю нагрузку: 150–300 единиц
учёта, до 10 человек, из которых пишет обычно один — тот, кто оформляет выдачу.
Читателей WAL не блокирует, а запись занимает миллисекунды, так что единственный
писатель SQLite ни разу не станет узким местом.

PostgreSQL здесь добавил бы вторую службу, которую надо ставить, настраивать,
обновлять и бэкапить отдельно, — и ничего не дал бы взамен. Он окупается, когда
появляется хотя бы одно из: несколько экземпляров приложения за балансировщиком,
десятки одновременных пишущих, репликация, или сторонние системы, которым нужен
прямой доступ к базе. Ничего из этого в задаче нет.

Резервная копия при SQLite — это копия одного файла, и её можно делать на живой
базе, не останавливая приложение:

```bash
python -c "import sqlite3; s=sqlite3.connect('data/inventory.db'); d=sqlite3.connect('backups/inv.db'); s.backup(d)"
```

Копировать файл базы через `cp` нельзя: при WAL часть свежих записей лежит в
`inventory.db-wal`, и такая копия окажется устаревшей. `backup()` собирает целостный
снимок сам.

Переезд на PostgreSQL, если он когда-нибудь понадобится, — это смена `database_url`,
удаление подмены `lower()` в `app/db.py` (в PostgreSQL регистр букв кириллицы
сворачивается сам) и перенос данных. Слой моделей и сервисов трогать не придётся.

### Docker

```bash
cp .env.example .env          # обязательно свой SECRET_KEY
docker compose up -d --build
```

Приложение на порту 8000. Миграции накатываются при каждом старте контейнера,
отдельного шага развёртывания нет. База и фотографии лежат на именованном томе
`inventory-data` и переживают пересборку образа — образ пересобирается, данные нет.

Первая учётная запись заводится внутри контейнера, пароль спрашивается в терминале
и никуда не записывается:

```bash
docker compose exec app python -m scripts.create_admin ivanov --role admin --full-name "Иванов И. И."
```

Резервная копия тома:

```bash
docker compose exec app python -c "import sqlite3; s=sqlite3.connect('/app/data/inventory.db'); d=sqlite3.connect('/app/data/backup.db'); s.backup(d)"
docker compose cp app:/app/data/backup.db ./backups/
```

### Чистый старт

После знакомства с демо-набором база очищается до одной учётной записи:

```bash
python -m scripts.reset_db --admin admin --with-types
```

Стираются справочники, сотрудники, единицы, журнал, расходники,
проекты и командировки.
`--with-types` оставляет стандартный набор из 19 типов единиц — без единого типа
нельзя завести ни одну единицу. `--keep-types` сохраняет те типы, что уже заведены.
Если учётка с указанным логином уже существует, она сохраняется вместе с паролем.

**Скрипт стирает данные безвозвратно — сделайте копию базы до запуска.**

## Комплекты и комплектность

Комплект поставки — обычная единица-контейнер, внутрь которой вложены части: базовая
станция, антенны, кабели. Отдельной сущности для этого нет, работает та же вложенность,
что и у системного блока с планками памяти.

Вложенное не перемещается отдельно: пока антенна лежит в комплекте, её размещение —
«внутри KIT-0001», и оно не меняется, когда комплект уезжает на площадку. Поэтому журнал
не засоряется дублями на каждую часть, а в карточке видно строку «фактически» — где
физически находится вещь по цепочке вложенности.

**Шаблон комплектности** — перечень того, что в комплекте должно быть: одна базовая
станция, две антенны, шесть кабелей. Шаблон назначается единице в её карточке, после чего
на странице «Комплекты» видно, чего не хватает и есть ли подходящее на складе.

## Личный кабинет сотрудника

Сотрудник входит своим логином и попадает в `/cabinet`. Учётные экраны отдела ему не
открываются: роль `employee` их не проходит, а попытка вернёт его обратно в кабинет.

| Раздел | Что там |
|--------|---------|
| `/cabinet` | своя техника со вложенным содержимым, блок «Ждут вашего подтверждения», своя командировка |
| `/cabinet/colleagues` | коллеги и что за каждым закреплено |
| `/cabinet/search` | поиск вещи по инвентарному, прежнему или серийному номеру — где она и у кого |
| `/cabinet/history` | что выдавали и что забирали, с датами |
| `/cabinet/act` | печатный акт закрепления на себя |

Кабинет только читает. Изменить он позволяет ровно одно: подтверждение собственного
получения, и оно проверяется по привязанной карточке сотрудника — чужое не подтвердить.

Что видно про коллег: ФИО, должность, отдел, кабинет и техника за ними — то же, что видно,
если пройти по кабинетам. Табельных номеров, журнала правок и учётных действий там нет.

## Склад и расходники

Два режима учёта рядом, намеренно не объединённые в один.

**Единицы** нумеруются поштучно, у каждой своя карточка и цепочка размещений.
**Расходники** — мыши, патч-корды, переходники, кабели питания — учитываются количеством:
у позиции есть остаток, порог «заканчивается», место хранения и журнал движений.

`/storage` показывает склад как места: шкафы с полками и ячейками, на каждой — сколько
единиц и сколько позиций расходников, с учётом вложенных мест. `/storage/{id}` открывает
конкретную полку: что на ней лежит поштучно и что количеством.

`/consumables` — список позиций с фильтрами по категории, месту и остатку. В карточке
позиции три операции, и других нет:

| Операция | Что пишет в журнал |
|----------|--------------------|
| Приход | `+N`, откуда поступило |
| Расход | `−N`, кому выдали или зачем списали — без этого не примет |
| Корректировка | разницу после пересчёта: видно, сколько не сошлось |

Остаток нельзя увести в минус и нельзя отредактировать формой: `ConsumableStock.quantity` —
такой же кэш, как размещение у единицы, и пишет его только `services/consumables.py`.
Сторож `services/stock_guard.py` роняет транзакцию, если количество меняют мимо сервиса.

Расходники, выданные человеку, видны в его карточке и у него в кабинете — они не
закрепляются и не возвращаются, это просто след выдачи. Отчёт «заканчивается» —
`/reports/low-stock`, он же плиткой на сводке.

## Командировки

Сотрудник уезжает и берёт технику с собой. Пока он в пути, вещь не «у него в кабинете»:
её размещение — «в командировке», а цель размещения — запись поездки, которая знает,
кто поехал и куда. Поэтому список того, что физически в здании, отвечает честно.

Командировка — это `Trip`: сотрудник, куда, зачем, даты выезда и возвращения, необязательный
проект. Номер свой: `TRIP-0007`. Оборудование записывается на поездку и снимается с неё
тремя способами, и других нет:

| Исход | Что происходит с размещением |
|-------|------------------------------|
| Вернулась | склад, кабинет или сотрудник — на выбор принимающего |
| Оставлена на месте | «передано за пределы отдела» с пометкой о командировке |
| Списана там | списано, обычным списанием из карточки единицы |

**Поездка не закроется, пока судьба каждой увезённой единицы не решена** — система назовёт
инвентарные номера тех, что ещё числятся в пути. В этом весь смысл раздела: техника не
теряется между «уехал» и «вернулся».

Вложенное едет вместе с контейнером: взять в командировку отдельно антенну, уложенную
в комплект, нельзя — берут комплект. Перемещения датируются днём выезда, а не днём, когда
поездку внесли в систему, так что задним числом всё записывается правильно.

Отъезд закрывает открытую выдачу: вещь, уехавшая с человеком, перестаёт висеть
в «не подтверждено» и «просрочен возврат» — она числится в поездке, и спрашивать
за неё надо по поездке.

Сотрудник видит свою командировку в личном кабинете: куда, на какие даты и что он
должен привезти обратно. Отдел видит на сводке плитку «В командировках» и предупреждение
«Не вернулись из поездки», когда срок прошёл, а вещи ещё там. `/trips/{id}/act` печатает
перечень выданного в командировку.

## Проекты

Часть техники — своя, часть приходит из проектов: куплена под него, привезена заказчиком,
по окончании возвращается ему. `Project` — справочник (код, название, заказчик, сроки,
состояние), `Item.project_id` — принадлежность.

Принадлежность **не** размещение: она меняется формой в карточке единицы, потому что
меняется вместе с бумагами, а не когда вещь несут в другой шкаф. Пустое поле значит
«числится на предприятии».

`/projects` — список с числом единиц за каждым проектом. `/projects/{id}` — карточка:
всё оборудование проекта с текущим размещением, разбивка «где оно» (на складе, у людей,
в командировках, на площадке), командировки по проекту и сколько списано. В списке единиц
есть фильтр принадлежности, складывающийся с остальными.

## Сводка

`/dashboard` — первая страница для отдела после входа. Плитки кликабельные, каждая ведёт
в список с наложенным фильтром: где что находится, сколько в ремонте, что не подтверждено,
что просрочено к возврату (`/reports/overdue`), сколько открытых заявок.

## Что за мной закреплено

Страница `/my` осталась для тех, кому учётную запись не заводили. Она открывается без входа:
сотрудник вводит табельный номер с пропуска
и видит перечень закреплённой за ним техники, включая то, что вложено внутрь (память
в системном блоке, части комплекта). Ссылка есть на странице входа.

Там же сотрудник подтверждает получение: свежие выдачи выводятся отдельным блоком
«Ждут вашего подтверждения» с кнопкой «Получил». Подтвердить можно только свою выдачу и
только один раз. Что осталось неподтверждённым, видно в отчёте `/reports/unconfirmed`.

Это опознание, а не проверка личности: табельный номер напечатан на пропуске, и тот, кто
его знает, увидит список и сможет нажать «Получил» за другого. Поэтому страница показывает
только технику — ни должности, ни кабинета, ни отдела, — а номер уходит методом POST и не
попадает в адресную строку, в историю браузера и в логи. Юридически значимая подпись —
по-прежнему на бумаге, для этого есть печатные акты.

## Печатные акты

- `/employees/{id}/act` — акт закрепления: всё, что сейчас числится за сотрудником.
- `/movements/{id}/act` — акт приёма-передачи по конкретной выдаче.

Обе формы свёрстаны под печать через `@media print`: шапка, кнопки и подсветка убираются,
остаётся таблица с инвентарными и серийными номерами и две строки для подписей.

## Учётные записи

Заводятся в разделе «Учётки» (`/admin/users`, только `admin`): роль, привязка к сотруднику,
включение и отключение, сброс пароля. Свой пароль каждый меняет в `/profile` — там смена
требует старого, так что администратор нового не видит.

Что интерфейс не даст сделать: понизить себе роль, отключить собственную запись, снять
роль с последнего администратора, привязать двух пользователей к одному сотруднику и
завести запись `employee` без карточки сотрудника.

Проверка учётных данных вынесена в провайдер (`app/auth/providers/`), чтобы позже
добавить LDAP/AD, не переписывая вход.

## Устройство кода

```
app/models      SQLAlchemy: Item, ItemType, Movement, справочники, User,
                ConsumableStock, Project, Trip
app/schemas     Pydantic: валидация форм и фильтров
app/services    бизнес-логика; move_item() — единственный вход к смене размещения
app/routers     HTTP: разбор формы, вызов сервиса, рендер шаблона
app/templates   Jinja2, весь текст на русском
app/static      один CSS-файл и htmx.min.js
alembic/        миграции
scripts/        создание учётной записи, демо-данные
tests/          сервисный слой и сквозные HTTP-проверки
```

Правило про журнал перемещений держится не на дисциплине: слушатель `before_flush`
в `app/services/location_guard.py` роняет транзакцию, если поля размещения меняются
вне `move_item()`. Создать `Item` в обход сервиса тоже нельзя — первая запись журнала
появляется вместе с единицей. Точно так же устроен `stock_guard.py` для остатка
расходников.

Поиск регистронезависим и по-русски: SQLite приводит к нижнему регистру только латиницу,
поэтому `app/db.py` подменяет её функцию `lower()` питоновской — `ilike` во всём
приложении начинает видеть «монитор» в «Мониторе».

## Ограничения

- QR-кодов и печати наклеек пока нет — отложено до отдельного решения. Единицы находят
  поиском по инвентарному или прежнему номеру.
- Заявок от сотрудников тоже нет: сломалось или нужна техника — говорят отделу словами.
  Раздел был сделан и снят, вернуть его можно откатом одного коммита.
- ФИО сотрудников — персональные данные: не логируются и не выводятся в URL.
- Единого входа (LDAP, домен) нет: пароли хранятся в приложении, argon2.
